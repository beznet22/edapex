# EdApex Drizzle Table Catalog — In-Use Subset

Every Drizzle table declared in `src/lib/server/db/sms-schema.ts` that is actually imported or referenced by application code under `src/`.

## Scope

| | |
|---|---|
| Tables declared in `sms-schema.ts` | **310** |
| Tables used by `src/` | **49** |
| Tables never imported by `src/` | **261** |
| Declared foreign keys (used tables) | 200 |
| Relations blocks parsed | 261 |

**Excluded by request:** `ai_sessions` (`src/lib/server/db/schema.ts`) and all 13 tables in `src/lib/server/mastra/storage/libsql/app-db.schema.ts`. Those are EdApex-owned sovereign-storage tables, not part of the 310 legacy SMS tables this catalog covers.

**How "used" is defined:** the export name appears in a named import, an aliased import, a `import * as ns` member access (`ns.smStudents`), or a dynamic `await import()` destructure from `sms-schema` / `db/schema`, **and** at least one reference to that binding exists in a `.ts`/`.svelte` file under `src/`. The schema layer itself (`sms-schema.ts`, `db/schema.ts`, `sms-relations.ts`) is excluded as a consumer — `sms-relations.ts` alone imports 261 tables, so counting it would mark every table "used".

`scripts/` and `tests/` are deliberately **not** counted toward inclusion.

## Reading the tables

- **PK** — primary key column(s). `chat_groups` declares none in source; that is a real schema-drift finding, not a parsing gap.
- **FK** — `column → target_table.target_column`, with the declared `onDelete` behaviour in `[brackets]` when the source specifies one.
- **Relations** — `one:` / `many:` edges from `sms-relations.ts`, restricted to tables in this catalog.
- **Source File** — a clickable link to the exact `export const` line in `sms-schema.ts`.
- **Used:** links point at real reference sites (repository, service, route, or Mastra tool), not at import statements.

All anchors reflect the tree state at catalog generation; regenerating after schema edits refreshes them.

## Notable findings

- **`chat_groups` has no primary key.** Its `id` is `char(36) NOT NULL` without `.primaryKey()`. It is the only table in this set without one; uniqueness of the surrogate key is enforced only by the application, and inserts must supply a UUID themselves.
- **`chat_group_users` has no declared foreign keys.** Membership rows are correlated by plain columns, so removing a chat group or changing a student's class requires the application to clean up manually — `student.repo.ts` does exactly that during class migration. Any new writer must repeat the cleanup.
- **`exam_merit_positions` is an unconstrained snapshot.** No FKs at all; it is rebuilt from `sm_result_stores`, so it can drift if results are edited without regenerating merit lists.
- **Two result layers are intentional.** `sm_mark_stores` holds raw per-subject marks and is rewritten on marksheet re-submission; `sm_result_stores` holds the computed grade/position and is what report rendering reads. Neither is redundant.
- **261 of 310 tables are dead weight to EdApex.** They remain in the Drizzle schema (and therefore in `drizzle-kit` diffs) but no code under `src/` imports them — including oddities such as the duplicated `continents`/`continets` pair.
- **45 of 49 tables are tenant-scoped through an explicit `school_id` FK.** The four without one are `chat_group_users` (no FKs at all), `exam_merit_positions` (derived snapshot), `student_ratings`, and `teacher_remarks` (both keyed by `(student, exam_type, academic_year)` instead). For those four, tenant isolation has to come from the surrounding query, not from the row.
- **`sm_general_settings` has no unique constraint on `school_id`**, despite being read as a single-tenant settings row. Duplicate rows are possible at the database level.

### The hygiene problem, in detail

There is not one permission model here — there are two half-built ones sharing a boundary nobody drew. Three facts, all read directly from the schema:

**1. Two role tables with the same columns.** `infix_roles` (L1689) and `roles` (L2223) are identical column-for-column (`id`, `name`, `type`, `active_status`, `created_by`, `updated_by`, `created_at`, `updated_at`, `school_id`) except that `infix_roles` adds `is_saas`. That is a fork, not two different concepts.

**2. The 19 role references split three ways** — 18 are columns named `role_id`, and one is `smLibraryMembers.member_type`, which points at `roles.id` despite its name.

| Points at | Tables |
|---|---|
| `infix_roles` (6) | `users`, `smStaffs`, `smStudents`, `smUserLogs`, `dueFeesLoginPrevents`, `infixPermissionAssigns` |
| `roles` (8) | `smDashboardSettings`, `smItemIssues`, `smItemSells`, `smLeaveDefines`, `smLeaveRequests`, `smLibraryMembers` (via `member_type`), `smModulePermissionAssigns`, `smRolePermissions` |
| **nothing — no FK at all** (5) | `assignPermissions`, `sidebars`, `smNotifications`, `smStudentIdCards`, `teacherEvaluations` |

The split is almost clean by domain: identity tables point at `infix_roles`, operational-module tables (leave, inventory, library, dashboards) point at `roles`. But `assign_permissions` and `sidebars` — the two tables that actually decide what a user may *do* — point at neither, and have no Drizzle relation either. A grant can name a role that does not exist.

**3. Two module-permission lineages doing the same job.**

| Lineage | Tables | Role table it uses |
|---|---|---|
| Infix | `infix_module_infos` → `infix_permission_assigns` | `infix_roles` |
| SMS | `sm_modules` → `sm_module_links` → `sm_module_permissions` → `sm_module_permission_assigns`, plus `sm_role_permissions` | `roles` |

### What to do, in order

**Step 1 — Write down the boundary, even if you change nothing else.** The least disruptive rule that fits the data as it stands: `infix_roles` means *who this person is* (auth, `TenantContext`, Mastra tool selection), and `roles` means *what module they can operate* (leave, inventory, library). Put that sentence in `docs/` next to the permissions work so the next table doesn't pick arbitrarily. Unifying instead is also valid — every table holding `roles.role_id` is currently unused, so re-pointing them costs nothing today, but it means editing 8 declarations, one of which is the misleadingly named `smLibraryMembers.member_type`.

**Step 2 — Give the 5 unconstrained `role_id` columns a foreign key.** This is the cheapest correctness fix here, and today those columns accept any integer: `assign_permissions.role_id`, `sidebars.role_id`, `sm_notifications.role_id`, `sm_student_id_cards.role_id`, `teacher_evaluations.role_id`. Add `.references(() => infixRoles.id, { onDelete: "set null", onUpdate: "restrict" })` (or `roles.id`, per Step 1) and the matching `relations()` blocks — `assignPermissionsRelations` currently links to `sm_schools` only.

**Step 3 — Pick one module lineage and freeze the other.** Use the Infix lineage: `infix_permission_assigns` is the only one already wired to a role table you read. Stop adding to `sm_module_*` and `sm_role_permissions`. You do not have to delete them to stop the bleed.

**Step 4 — Prove the tables are empty before deleting anything.** I have not connected to your database; these counts are yours to run:

```sql
SELECT 'infix_roles' AS t, COUNT(*) AS n FROM infix_roles
UNION ALL SELECT 'roles', COUNT(*) FROM roles
UNION ALL SELECT 'permissions', COUNT(*) FROM permissions
UNION ALL SELECT 'assign_permissions', COUNT(*) FROM assign_permissions
UNION ALL SELECT 'permission_sections', COUNT(*) FROM permission_sections
UNION ALL SELECT 'sidebars', COUNT(*) FROM sidebars
UNION ALL SELECT 'infix_permission_assigns', COUNT(*) FROM infix_permission_assigns
UNION ALL SELECT 'sm_module_permission_assigns', COUNT(*) FROM sm_module_permission_assigns
UNION ALL SELECT 'sm_role_permissions', COUNT(*) FROM sm_role_permissions;
```

And check whether the two role tables actually disagree, before deciding one is disposable:

```sql
SELECT r.id, r.name AS roles_name, ir.name AS infix_name
FROM roles r
LEFT JOIN infix_roles ir ON ir.id = r.id
WHERE ir.id IS NULL OR ir.name <> r.name;

SELECT COUNT(*) AS orphan_grants
FROM assign_permissions a
LEFT JOIN infix_roles r ON r.id = a.role_id
WHERE r.id IS NULL;
```

**Step 5 — Only then remove the loser.** If a table is empty, drop it in a normal `drizzle-kit generate` migration, and remove its export from `sms-schema.ts` in the same commit. If it has rows, migrate them first — do not add FKs to data you have not looked at.

**Step 6 — Put role and permission reads behind one module.** A single module (for example `src/lib/server/permissions/`) that is the only importer of these tables. That turns "which role table?" from a convention someone has to remember into the only code path that exists — and it keeps the decision out of individual Mastra tools.

**What this buys you:** today the coarse gate (`is_administrator` + `designationId` + `roleId`) works because it is small. The moment `permissions` and `assign_permissions` come online, the unconstrained `role_id` columns and the two role tables become a correctness problem rather than untidiness — which is why Step 2 should land before Step 3's granular RBAC work, not after.
