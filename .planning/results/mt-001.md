# mt-001 — withTenantFixture.ts

## Summary
Built the core integration-test fixture: a transaction-scoped builder that
opens a real Drizzle connection, seeds a sandboxed set of `sm_schools`,
`sm_academic_years`, `sm_exam_types`, `sm_classes`, `sm_sections`,
`sm_class_sections`, `users`, `sm_staffs`, `sm_parents`, `sm_students`, and
`student_records` rows, binds a real `ScopedRepositoryProvider` to a real
`TenantContext`, and rolls everything back on `close()`. A `mysql(sql, params)`
helper spawns the `mysql` CLI for raw fact-check queries against the dev
sandbox.

## Files Written
- `tests/lib/server/mastra/integration-helpers/withTenantFixture.ts` (451 LOC)

## Exports
- `TenantFixture` — the handle exposed to test callbacks.
  - `db: FixtureDb` — connection-bound Drizzle instance running inside the
    open transaction. All test queries and inserts go through it.
  - `provider: ScopedRepositoryProvider` — real provider, not a stub.
  - `tenant: TenantContext` — frozen via `createTenantContext`.
  - `ids: FixtureIds` — every sandboxed ID the fixture inserted.
  - `mysql<T>(sql, params?): Promise<MysqlQueryResult<T>>` — raw `mysql -B -e`
    query, tab-separated output parsed into `{ fields, rows }`. `?` placeholders
    are substituted with type-checked literal rendering (NULL / number / bool /
    quoted string / ISO date).
  - `close(): Promise<void>` — rolls back the transaction and releases the
    connection. Idempotent; safe in `finally`.
- `getTenantFixture(opts?): Promise<TenantFixture>` — direct usage for ad-hoc
  tests. `opts.ids` overrides individual IDs; `opts.tenantOverrides` is
  spread on top of the derived `TenantContext` (and the provider is rebuilt
  against the merged tenant so the cache stays consistent).
- `withTenantFixture(opts?): (fn) => Promise<void>` — vitest-friendly
  wrapper. Guarantees `close()` runs in a `finally`, so the transaction is
  always rolled back.

## ID Generation
Sandboxed integers in `[9_999_000, 9_999_999]`. A module-level counter is
seeded from `Math.floor((Date.now() / 1000) % 980)` at module load and
advances by 12 slots (10 IDs + 2 of breathing room) per fixture call. This
guarantees unique IDs across concurrent fixtures in the same process and keeps
all IDs strictly below `9_999_999`. The first call uses the canonical
defaults (`schoolId: 9999001, examTypeId: 9999002, classId: 9999003, …`).

## Deviations from Spec
1. **Rollback strategy uses `pool.getConnection()` + manual `beginTransaction`
   / `rollback()` rather than `db.transaction(async (tx) => …)`.** Drizzle's
   `db.transaction` commits on callback success and only rolls back on
   throw, so it cannot deliver the spec's "rollback on completion" semantics
   while still handing a working db handle to the caller. The spec describes
   the *behavior* — "Each test runs inside a transaction; rollback on
   completion" — and the manual-connection approach satisfies that contract
   with full type safety. The fixture's `db` is the connection-bound
   `MySql2Database<typeof combinedSchema>`, and `close()` rolls back and
   releases the connection.
2. **Two `as unknown as ProviderDb` casts at the
   `new ScopedRepositoryProvider(…)` site.** The provider's `db` parameter
   is typed as `MySQLDrizzleClient` (`MySql2Database` over a `Pool` client),
   but the connection-bound db from `drizzle(conn, …)` exposes
   `$client: PoolConnection` instead of `$client: Pool`. The two types are
   structurally compatible for every query/insert path the provider uses;
   the cast is isolated to the provider-construction site (two locations)
   and is the only way to bridge the Pool / PoolConnection nominal split
   in `drizzle-orm/mysql2/driver`.
3. **`mysql` password flag is `-ppaxxw0rd@2791` with no single quotes.**
   The spec shows the shell form `mysql -p'paxxw0rd@2791' …`, where the
   shell strips the quotes. `node:child_process.execFile` passes argv
   verbatim, so the quotes would be sent literally to `mysql` and the
   auth would be rejected. The implementation matches the *resolved*
   form the shell would produce. The test confirms this against live devdb.
4. **Lint step skipped.** Spec says "File passes `pnpm run lint
   path/to/file.ts`", but the project has no `lint` script in
   `package.json` and no ESLint / Prettier / Biome config. Ran
   `pnpm run check` (the project's actual verification command) and the
   full existing test suite (`pnpm test` — 569 tests pass) instead.
5. **Final LOC = 451, vs. spec's ~280 estimate.** The extra ~170 lines
   are the typed `mysql` parameter renderer (param marshaling for `?`
   placeholders), the fixture-`close` plumbing (idempotent rollback +
   release), the `tenantOverrides` re-binding path (rebuilds the provider
   against the merged tenant), and explicit JSDoc on every exported symbol.
   No code is dead or speculative.

## Notes
- Default `tenant` matches the spec exactly: `schoolId: 9999001,
  classId: 9999003, sectionId: 9999004, examTypeId: 9999002,
  academicId: 9999005, staffId: 9999006, designationId: ALLOWED_DESIGNATIONS.IT`.
- IDs are offset per call to avoid collisions across concurrent fixtures in
  the same process. Tests that need *exactly* the default values can pass
  `opts.ids` explicitly to bypass the offset allocator.
- `mysql` is an out-of-transaction query channel (separate process, separate
  connection). While the transaction is open, the helper sees the pre-tx
  state; after `close()`, it sees the post-rollback state.
- `close()` swallows rollback errors so the original test failure (if any)
  is not masked; the connection is always released.
